AC 40: Final Update

Story titleGoogle UCP | Order Lifecycle API | Get Order Mulesoft Endpoint

Description Acceptance Criteria Test Scenarios Architectural Solution Implementation details Open questions

Description

User story: As Google UCP (the API consumer), I want to call GET /orders/{id}, So that I can retrieve the latest snapshot of an order's status on demand.

Develop a MuleSoft API that returns the order's current-state snapshot: the full UCP order entity most recently sent to Google by the order-lifecycle webhooks (AC-23, AC-24, AC-25, AC-35, AC-38), stored in ucp_order_latest_status and looked up by order id and brand through the Postgres System API. Implement the endpoint according to the UCP Get Order REST specification, version 2026-04-08. The links in the Acceptance Criteria point to ucp.dev/latest; read them at 2026-04-08.

Include request validation, authentication, order-level authorization, backend integration, response mapping, error handling, and request tracing.

Acceptance Criteria

  1. Expose GET /orders/{id} with a required string order ID. Serve the endpoint over HTTPS with TLS 1.3 or higher. The Request-Id and UCP-Agent headers are not validated by this API or its gateway. REST requirements
  2. Request must include a valid OAuth JWT bearer token; unauthenticated or invalid-token requests are rejected with 401 Unauthorized. Token validation sits on each brand's Flex Gateway (AC-39), which also sets the brand (AC 8); test it through the gateway, not against the API directly.
  3. For an existing order, return HTTP 200 with Content-Type: application/json. Include required fields: ucp, id, checkout_id, permalink_url, line_items, fulfillment, currency, and totals. Return the stored snapshot's fields as they are. Currency must match the originating checkout. Response contract
  4. Return the order snapshot as stored in ucp_order_latest_status, without changing it. Its completeness and ordering are the responsibility of the order-lifecycle stories (AC-23, AC-24, AC-25, AC-35, AC-38). Order data model
  5. For a missing order, an order of the other brand, or an order whose stored snapshot is empty, return the documented HTTP 200 business-error envelope with ucp.status: "error", a message with code not_found and severity unrecoverable. Do not return HTTP 404. Error examples
  6. Downstream Postgres SAPI failures return 503 Service Unavailable with a generic error message; the caller receives no internal detail or stack trace.
  7. MUnit tests cover successful retrieval, optional-field handling, invalid requests, missing orders, other-brand and empty-snapshot orders, and backend failures. Publish the API contract and request/response examples in Anypoint Exchange.
  8. The brand is taken from the brand header set by the brand's Flex Gateway (gracobaby or yankeecandle), never from the caller, and the order lookup matches the value the order-lifecycle application stores for that brand.
  9. An order that has been completed but whose Order Created event has not yet been processed returns the same not_found envelope as a missing order, never a server error.

Test Scenarios

  1. Through the brand's gateway with a valid token, call GET /orders/{id} for an existing order and confirm HTTP 200, Content-Type: application/json, and a body with ucp, id, checkout_id, permalink_url, line_items, fulfillment, currency and totals, with currency equal to the checkout's.
  2. Connect to the endpoint with TLS 1.2 only and confirm the connection is refused; connect with TLS 1.3 and confirm it succeeds.
  3. Through the gateway, send no token, an expired or invalid token, and a token for the other brand, and confirm 401 each time.
  4. Request an existing order and confirm the response equals the stored snapshot, with no fields added, removed or changed.
  5. Request an order id that does not exist and confirm HTTP 200 with ucp.status: "error" and one message type: "error", code: "not_found", severity: "unrecoverable", and no order fields.
  6. Through the Yankee Candle gateway, request a Graco order id, and confirm HTTP 200 with code: "not_found", severity: "unrecoverable".
  7. Request an order whose stored snapshot is empty and confirm the not_found envelope, never a 200 "No data found" body.
  8. Through the Graco gateway, request a Graco order placed through Google and confirm it is found.
  9. Send a request with a caller-supplied brand header that differs from the gateway's brand and confirm the gateway's brand is the one used.
  10. Make the Postgres System API unavailable and confirm HTTP 503 with a generic body (no stack trace or internal host names); make it slow and confirm the response returns within 10 seconds.
  11. Complete a checkout and call Get Order immediately, before the Order Created event has been processed, and confirm HTTP 200 with code: "not_found".
  12. Run the MUnit suite and confirm it covers successful retrieval, optional fields, invalid requests, missing orders, other-brand and empty-snapshot orders, and backend failures; confirm Exchange shows GET /order/{orderId} (reached by Google as GET /orders/{id}) with UCP request and response examples.

Precondition: run these through each brand's Flex Gateway, which validates the token, rewrites the path and sets the brand. Called directly, the API answers with its own client-id policy and the /order/{orderId} path.

Architectural Solution

Each brand has a Flex Gateway proxy (Graco, Yankee Candle). The proxy validates the OAuth JWT and TLS, rewrites GET /orders/{id} to this API's GET /order/{orderId}, and sets the brand header (gracobaby or yankeecandle), overwriting any value from the caller. It also supplies the Anypoint client credentials.

The API itself only reads. It looks up the order by id and brand in ucp_order_latest_status through the Postgres System API, and returns the stored UCP order entity unchanged. The lifecycle webhooks (AC-23, AC-24, AC-25, AC-35, AC-38) write that table.

Implementation details

  • Found: HTTP 200 with the stored snapshot.
  • Missing order, other-brand order, empty snapshot, or an order not yet processed: HTTP 200 with the UCP error envelope, code: "not_found", severity: "unrecoverable".
  • Postgres System API failure or timeout: HTTP 503 with a generic body. The System API timeout is 10 seconds.
  • Invalid or missing orderId or brand (anything other than letters, digits, - and _, up to 64 characters): HTTP 400.
  • Logging: Splunk gets only order id, status, brand and site. The snapshot, which holds the shopper's name and address, is never logged.
