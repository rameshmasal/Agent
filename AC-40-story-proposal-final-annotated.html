Description

Two edits to the Description field. Everything not listed stands as written.

User story: As Google UCP (the API consumer), I want to call GET /orders/{id}, So that I can retrieve the latest snapshot of an order's status on demand.

Edit 1 — what the endpoint returns, and where it comes from

Develop a MuleSoft API that retrieves an order from the backend order system and uses DataWeave to transform it into a UCP-compliant current-state response.

Develop a MuleSoft API that returns the order's current-state snapshot: the full UCP order entity most recently sent to Google by the order-lifecycle webhooks (AC-23, AC-24, AC-25, AC-35, AC-38), stored in ucp_order_latest_status and looked up by order id and brand through the Postgres System API.

UCP says "The same schema is used for both synchronous retrieval … and asynchronous event delivery", so the stored webhook payload already is the Get Order response, with no second mapping to keep in step. The response is therefore never fresher than the last webhook (AC 4), and an order has no stored snapshot until its Order Created event has been processed (AC 9).

Edit 2 — pin the spec version

Implement the endpoint according to the UCP Get Order REST specification (ucp.dev/latest/specification/shopping/order/rest/#get-order).

Implement the endpoint according to the UCP Get Order REST specification, version 2026-04-08 (https://ucp.dev/2026-04-08/specification/order-rest/#get-order). The links in the Acceptance Criteria point to ucp.dev/latest; read them at 2026-04-08.

latest now serves version 2026-08-25, which moved these pages to shopping/order/… and added an optional policies[] field. Get Order itself is unchanged, but the rest of the integration, and the ucp.version this endpoint returns, is 2026-04-08.

Stands as written

"Include request validation, authentication, order-level authorization, backend integration, response mapping, error handling, and request tracing."

Status

The code now matches the criteria: the endpoint returns the stored UCP order entity scoped by brand, answers misses with the UCP not_found envelope, returns 503 on a backend failure, and logs only id, status, brand and site. 8 MUnit tests pass and the contract is published to Exchange. Still to confirm in QA: the 503 with a forced database failure, and the end-to-end calls through the gateways for scenarios 1, 8 and 11.

Acceptance Criteria

The seven existing criteria keep their number and order, and each carries a text edit (a strike-through is removed text, bold is added). Two new criteria are appended as 8–9.

  1. UpdatedHighCode: To verifyExpose GET /orders/{id} with a required string order ID. Validate required Request-Id and UCP-Agent headers; the latter must contain a profile URL ending in /.well-known/ucp using RFC 8941 dictionary syntax. Serve the endpoint over HTTPS with TLS 1.3 or higher. The Request-Id and UCP-Agent headers are not validated by this API or its gateway. REST requirements

    What changed and why: The sentence that required Request-Id and UCP-Agent validation (the latter as an RFC 8941 profile URL ending in /.well-known/ucp) is replaced by a statement that they are not validated. Decision: the brand gateways are called with Authorization only and do not check them. UCP lists both headers as required, but Google sends them anyway, so ignoring them breaks nothing.

    Where it is met: each brand's Flex Gateway terminates TLS 1.3 and rewrites GET /orders/{id} to the API's GET /order/{orderId}. The API itself listens on plain HTTP behind the gateway, so test path and TLS through the gateway.

  2. UpdatedHighCode: To verifyRequest must include a valid OAuth JWT bearer token; unauthenticated or invalid-token requests are rejected with 401 Unauthorized. Token validation sits on each brand's Flex Gateway (AC-39), which also sets the brand (AC 8); test it through the gateway, not against the API directly.

    What changed and why: One sentence added. The API has no JWT check of its own: its RAML applies the Anypoint client-credentials trait, which the gateway satisfies with its own credentials. Tested directly against the API this criterion would fail for the wrong reason.

  3. UpdatedHighCode: ImplementedFor an existing, accessible order, return HTTP 200 with Content-Type: application/json. Include required fields: ucp, id, checkout_id, permalink_url, line_items, fulfillment, currency, and totals. Map optional fields when available and permitted. Return the stored snapshot's fields as they are. Currency must match the originating checkout. Response contract

    What changed and why: "accessible" is dropped (an order of the other brand is now simply not found, see AC 5), and "Map optional fields" becomes "Return the stored snapshot's fields as they are", because the API does no mapping: it returns the payload last sent to Google. The required list matches the 2026-04-08 order schema.

    Inherited from the lifecycle stories: checkout_id is dropped from the payload when the checkout row has a null ucp_session_id (AC-23 AC 2), and permalink_url uses a hard-coded path (AC-23 TS 5).

  4. UpdatedHighCode: ImplementedReturn the full latest order snapshot, including all historical line items, current quantities and statuses, fulfillment expectations and events, and available adjustments. Preserve monetary amounts in the currency’s minor units and signed adjustment values. Return the order snapshot as stored in ucp_order_latest_status, without changing it. Its completeness and ordering are the responsibility of the order-lifecycle stories (AC-23, AC-24, AC-25, AC-35, AC-38). Order data model

    What changed and why: The line is replaced. This API only reads the stored row and returns it, so it cannot make the snapshot more complete or decide ordering. Completeness, minor-unit amounts and signed adjustments are the lifecycle stories' responsibility.

    Known gaps in the lifecycle app: the latest-status row is upserted on order_id with no ordering check (sf-common-subflows.xml line 234), so a late Shipped event can replace a Delivered snapshot; and the Shipped and Cancelled payloads leave out earlier events or adjustments (AC-24 AC 13, AC-25 AC 6, AC-35 AC 20). Fixing these fixes this endpoint too.

  5. UpdatedHighCode: ImplementedFor missing or inaccessible orders, an order of the other brand, or an order whose stored snapshot is empty, return the documented HTTP 200 business-error envelope with ucp.status: "error", and an error message containing not_found or unauthorized, respectively, with severity unrecoverable a message with code not_found and severity unrecoverable. Do not return HTTP 404. Error examples

    What changed and why: Decision Q-40-02: an order of the other brand returns not_found, not unauthorized. The lookup is already scoped by the brand the gateway sets, so a second lookup by order id alone, just to say unauthorized, would add a database call for a rare case. An empty stored snapshot is treated as missing.

    Code: a miss or an empty snapshot now returns order-not-found.dwl, the UCP envelope with HTTP 200. Before, it returned HTTP 404 with a Newell body, and an empty snapshot returned 200 "No data found".

  6. UpdatedMediumCode: To verifyDownstream Postgres SAPI failures return 503 Service Unavailable with a descriptive generic error message; the caller does not receive internal stack traces receives no internal detail or stack trace.

    What changed and why: 502 Bad Gateway becomes 503 Service Unavailable (UCP lists 503 for temporary unavailability and has no 502; AC-18 already uses 503). "Descriptive" becomes "generic": the earlier code passed the System API's own error text through to the caller.

    Code: System API, HTTP, connectivity and timeout errors now return 503 with "Service temporarily unavailable" (service-unavailable-response.dwl); any other error returns a generic 500. The System API timeout is 10 seconds (was 120). Confirmed by MUnit; a forced failure in QA is still to be checked.

  7. UpdatedMediumCode: ImplementedMUnit tests cover successful retrieval, optional-field handling, invalid requests, missing orders, unauthorized access other-brand and empty-snapshot orders, and backend failures. Publish the API contract and request/response examples in Anypoint Exchange.

    What changed and why: "unauthorized access" is replaced because other-brand orders now return not_found (AC 5).

    Code: src/test/munit now holds 8 tests: success, optional fields absent, invalid order id, invalid brand, missing brand, missing order, empty snapshot, backend failure. They pass. The RAML now describes the UCP order, the not_found envelope and the 503, and has been published to Exchange.

  8. NewHighCode: ImplementedThe brand is taken from the brand header set by the brand's Flex Gateway (gracobaby or yankeecandle), never from the caller, and the order lookup matches the value the order-lifecycle application stores for that brand.

    Why we added it: The story never says how the brand is known. Gracobaby is stored under gracobaby by the lifecycle app (ucp.siteCodeToBrand.gracobaby in qa, uat and prod), so the gateway must send that value, not graco; with graco every Graco order would be not found. The gateways send brand (not X-Brand) and overwrite any caller value.

    Code: the API reads the brand header and matches the stored value as sent. Testing also found that the original input check had an operator-precedence flaw that let a missing or malformed brand through to the database filter. It now rejects them with 400.

  9. NewMediumCode: ImplementedAn order that has been completed but whose Order Created event has not yet been processed gets a defined response [Q-40-01] returns the same not_found envelope as a missing order, never a server error.

    Why we added it: The table row is written only when the lifecycle app processes the OMS New event, which happens after OMS's 2-minute batch and the queue delivery. Until then Get Order finds nothing, even though Google already holds the order id. Decision Q-40-01: return not_found in that window. The alternative, a minimal order built from the checkout, would make this API build orders instead of returning the stored snapshot.

Architectural Solution

Each brand has a Flex Gateway proxy (Graco, Yankee Candle). The proxy validates the OAuth JWT and TLS, rewrites GET /orders/{id} to this API's GET /order/{orderId}, and sets the brand header (gracobaby or yankeecandle), overwriting any value from the caller. It also supplies the Anypoint client credentials.

The API itself only reads. It looks up the order by id and brand in ucp_order_latest_status through the Postgres System API, and returns the stored UCP order entity unchanged. The lifecycle webhooks (AC-23, AC-24, AC-25, AC-35, AC-38) write that table.

Implementation details

  • Found: HTTP 200 with the stored snapshot.
  • Missing order, other-brand order, empty snapshot, or an order not yet processed: HTTP 200 with the UCP error envelope, code: "not_found", severity: "unrecoverable".
  • Postgres System API failure or timeout: HTTP 503 with a generic body. The System API timeout is 10 seconds.
  • Invalid or missing orderId or brand (anything other than letters, digits, - and _, up to 64 characters): HTTP 400.
  • Logging: Splunk gets only order id, status, brand and site. The snapshot, which holds the shopper's name and address, is never logged.
